## Commands

```sh
cmake -S . -B build                                   # tests are on by default (SPANIO_BUILD_TESTS)
cmake --build build --config Debug
ctest --test-dir build -C Debug --output-on-failure   # all test executables
ctest --test-dir build -C Debug -R test_socket_ops    # one test executable
build/tests/Debug/test_socket_ops.exe close_socket    # only the cases whose name contains "close_socket"
```

- `spanio::spanio` is an INTERFACE target that carries the include path, C++17, `Threads::Threads` and `ws2_32` (on Windows). The CMake option `-DSPANIO_ENABLE_LOG=ON` turns on the `detail::log_error` hook in `platform.h`. `-DSPANIO_WINDOWS_USE_AFD_REACTOR=ON` makes `make_platform_proactor` use the AFD readiness emulation on Windows instead of native IOCP. `test_io_proactor` runs every case against all backends of the platform regardless of this option.
- Tests use the project's own zero-dependency framework, `tests/test_framework.h`:
  - Define a case with `SPANIO_TEST(name)`.
  - `SPANIO_CHECK` records a failure and continues the case; `SPANIO_REQUIRE` records a failure and stops the case.
  - A filter that matches no case exits with failure.
- `tests/test_net_helpers.h` holds the shared loopback helpers: `socket_guard`, `make_loopback_listener`, `make_tcp_pair`, and others. Use it instead of re-writing socket setup in each test. `tests/test_proactor_backends.h` lists every proactor backend of the platform (`backends()`, `announce()`); tests that must cover all backends loop over it (`test_io_proactor`, the I/O cases of `test_io_context`). `test_io_reactor` runs through `make_platform_reactor`, so the same cases cover IOCP-AFD on Windows and epoll on Linux.
- To add a test executable, create `tests/<name>.cpp` and append `<name>` to `SPANIO_TEST_NAMES` in `tests/CMakeLists.txt`. Tests build with `/W4 /WX /permissive-` (MSVC) or `-Wall -Wextra -Wpedantic -Werror` (GCC/Clang).
- The Visual Studio solution is `build/SpanIO.slnx`, generated by `cmake -S . -B build`. It is a generated file, so change projects through the CMakeLists files, never the `.vcxproj` files.
  - `spanio_headers` and `spanio_docs` are IDE-only targets that make headers and docs visible; they build nothing.
  - New headers are picked up through a `CONFIGURE_DEPENDS` glob, but a new test must be added to `SPANIO_TEST_NAMES`.
- On the development machine, Windows builds use VS 2026 (the default CMake generator). No Linux toolchain is installed (no WSL), so the Linux code paths have not been compiled or run locally.

Planned, from the design doc:
- C++17 minimum; the coroutine module needs C++20. Backends will be picked in CMake with `if(WIN32)` / `if(UNIX)`. A `spanio_demo.sln` is also planned (the CMake VS generator can produce it).
- Windows links `ws2_32.lib`; Linux needs nothing extra (`liburing` only when the io_uring backend is on).
- Single-file compile of an example (the goal: one source file builds on both platforms):
  - Linux: `g++ -std=c++17 -Iinclude examples/echo_server.cpp -o echo_server -lpthread`
  - Windows: `cl /std:c++17 /Iinclude examples\echo_server.cpp ws2_32.lib`
- Optional feature macros, **all off by default**: `SPANIO_ENABLE_SSL`, `SPANIO_ENABLE_IO_URING`, `SPANIO_ENABLE_COROUTINE`, `SPANIO_ENABLE_LOG`. `SPANIO_SEPARATE_COMPILATION` turns on the optional static-library build. So far only `SPANIO_ENABLE_LOG` has a CMake option; add each of the others along with its module.
- Known platform difference: closing an already-closed socket returns `WSAENOTSOCK` on Windows, which does **not** compare equal to `std::errc::bad_file_descriptor`. Do not rely on a specific error code for that case.

## Architecture

SpanIO is a header-only C++17 network library for Linux and Windows with no third-party dependencies (no Boost). It is modeled on Asio, but aims for a smaller API. The layers, from the bottom up:

1. **Platform adapter** (`include/spanio/detail/`) is the only place where platform differences are handled. `platform.h` holds platform macros and `native_handle_t`. `socket_ops.h` provides `detail::close_socket`, `last_error`, `set_nonblocking`; WSAStartup runs once from a static RAII singleton, and every error becomes a `std::error_code`. Each backend implements the abstract `detail::io_reactor` (`add/mod/del/poll`):
   - `epoll_reactor` (Linux default), implemented
   - `iocp_reactor` (Windows), implemented
   - `io_uring_reactor` (Linux, optional), planned for M5
   - `select_reactor` (both platforms), planned

   The `io_reactor` contract, implemented in `io_reactor.h` and documented in design doc v0.2, sections 4.2 and 8.4:
   - **Level-triggered on every backend**: epoll does not use ET. `add/mod/del` return `std::error_code`; `poll(out, timeout_ms, ec)` takes an error code; `interrupt()` wakes a blocked `poll`.
   - `kEventError` and `kEventHangup` are always reported.
   - `add/mod/del/interrupt` may be called from any thread. Only one thread may call `poll` at a time.
   - `del()` must be called **before** the socket is closed.
   - `make_platform_reactor(ec)` in `platform_reactor.h` picks the backend for the platform.

   `iocp_reactor` gets readiness through the **undocumented `IOCTL_AFD_POLL`** on a `\Device\Afd` handle bound to an IOCP (the wepoll/libuv/mio technique), with ntdll functions loaded at run time:
   - Each socket has one in-flight request. The kernel writes into `afd_socket_state` until that request's completion packet is processed, so a state is never freed while a request is pending. `del()` moves it to `m_zombies`, and the destructor cancels requests and drains completions.
   - Level-triggered behaviour is emulated by re-submitting, at the start of the next `poll()`, a request for each socket that reported events.

   **`io_proactor`** (`io_proactor.h`, design doc 4.4) is the completion interface that the execution engine will use; it never talks to `io_reactor` directly. The interface:
   - Callers own an `io_operation`, fill it with `prepare_accept/connect/recv/send/post`, `start()` it, and get it back from `poll()` with `m_ec`, `m_bytes` and `m_accepted` filled in.
   - Every operation comes back **exactly once**, including failures and cancellations. `start()` never completes synchronously.
   - A cancelled operation reports `errc::operation_canceled` on every backend.
   - Each socket allows at most one read-side operation and one write-side operation at a time.
   - Before closing a socket, call `unregister_handle`. Before destroying a proactor, every operation must have come back.

   The two implementations:
   - `iocp_proactor` is the Windows default. It uses native `AcceptEx/ConnectEx/WSARecv/WSASend` and documented APIs only.
     - `io_operation::m_overlapped` must stay the first member: completions are cast back from `OVERLAPPED*`.
     - Calls that fail immediately are re-posted to the port by hand, to keep the exactly-once promise.
     - Errors go through `WSAGetOverlappedResult`, so their Winsock codes match the adapter's.
   - `reactor_proactor` wraps any `io_reactor`. It is the Linux default, and the Windows choice when `SPANIO_WINDOWS_USE_AFD_REACTOR` is defined.
     - It tries the I/O speculatively in `start()`.
     - It parks an operation on its socket only when the I/O would block.
     - It `add`s a socket to the reactor only while an operation is parked, and `del`s it when none is. Error and hang-up events are always reported, so keeping an idle socket in a level-triggered reactor would make `poll()` spin.

   `make_platform_proactor(ec)` in `platform_proactor.h` picks the backend.
2. **Execution engine**: `io_context` (implemented, design doc v0.4 section 5.3), `executor`, and `strand` (planned for M3; handlers bound to one strand never run at the same time). `io_context` follows Asio's semantics:
   - Users call `run()` from their own threads; the context creates none. Work = queued handlers + started I/O operations not yet completed + live `executor_work_guard`s. `run()` returns when work reaches zero or on `stop()`; the context is then `stopped()` and needs `restart()`.
   - With several threads in `run()`, exactly one at a time is the poller inside `io_proactor::poll()` (the proactor allows only one); it turns completed operations into queued handlers. The others wait on a condition variable. `post()` wakes an idle thread, or `interrupt()`s the poller if no thread is idle.
   - `post()` never runs inline; `dispatch()` runs inline when the calling thread is inside this context's `run()` (tracked by a thread-local frame stack). A throwing handler propagates out of `run()` and the context stays consistent.
   - Task nodes (`detail/scheduler_op.h`) dispatch through a function pointer, not virtual functions. An I/O node `io_op<Handler>` derives from both `io_operation` and `scheduler_op`, so one heap object goes through the proactor and then the task queue. Each node is completed (run or destroyed) exactly once and frees itself first, so a throwing handler leaks nothing.
   - I/O objects use the internal interface `register_handle / unregister_handle / cancel_handle / start_io(make_io_op(handler))`; the handler receives a `detail::io_result`.
   - The destructor destroys unrun handlers without calling them, after collecting every started I/O operation from the proactor (their sockets must already be cancelled or unregistered). It gives up after 5 s and leaks rather than free memory the kernel may still write.
3. **Unified API**: `tcp::acceptor`, `tcp::socket`, `udp::socket`, `timer`, `resolver`. Each object is constructed with an `io_context`, starts `async_*` operations, and gets results through a handler `(std::error_code, result)`.

**Proactor semantics on every platform**: when a handler runs, the data is already in the user's buffer.
- On Windows (by default), the native IOCP proactor delivers real completions.
- On Linux (and on Windows with the AFD option), `reactor_proactor` waits for readiness, does the `recv`/`send` itself, and returns the finished operation.
- The execution engine only sees `io_proactor`, so it has a single code path on every platform.
- On Linux with io_uring, operations are submitted to the SQ and their completions are collected from the CQ.

Callback, future and coroutine styles all run on the same completion events and differ only in the CompletionToken.

Non-goals: HTTP/2, WebSocket and QUIC; requiring C++20.

Known inconsistencies in the design doc: the umbrella header is called both `spanio.h` (file layout) and `spanio.hpp` (examples), and the sample code puts the brace on the same line as `if`, which the code rules below forbid. **Follow `code_rule.md`.**

## Coding rules (`docs/code_rule.md`, strictly enforced)

- **Braces:** every opening `{` goes on its own line, **except** for `namespace`. Nested namespaces are opened on a single line and are not indented: `namespace A { namespace B {` … `}}`.
- **Control flow:** the body of `if`/`for`/`while` always goes on its own line inside braces, even if it is a single statement.
- **No magic numbers:** use named constants or macros, each with a comment explaining it. Every `enum` value needs a comment explaining what it is for.
- **Member variables:** names start with an `m` prefix (`m_value`), and each one has a comment explaining its purpose.
- **Classes and methods:**
  - Every new class has a comment explaining its purpose.
  - Every public method has a comment covering what it does, each parameter, and the return value.
- **File header:** every `.h`/`.cpp`/`.c` file starts with a header block giving the file's purpose and usage, the developer (`lzwcracker@gmail.com`) and the date of development.
- **Comments:**
  - All comments are in **English**, even though the docs are in Chinese.
  - Comments make up at least 30% of the code, and none of them are filler.
- **Logging:** critical paths must log, so that problems can be located quickly.

## Testing and process rules

- If you are unsure how a feature behaves, run the tests first, and change code only after they pass.
- Every new feature needs test cases, and **the test-case design must be confirmed with the developer before it is implemented**.
- Mark speculative statements with "据推测" (speculatively) and then verify them. Back every conclusion with evidence.

## Git conventions (`docs/git_code_rule.md`)

- **Branch names:** `<name>/<type>/<camelCaseTopic>`, for example `zhangxf/feat/parseSqlPattern`.
- **Commit messages:** `<type>: <message>`, with several items separated by `;`.
- **Types:**
  - `feat`: a feature; also use it when a commit mixes a feature with fixes
  - `fix`: a bug fix
  - `chore`: non-functional changes such as style, typos and renames
  - `docs`: documentation
  - `test`: tests
  - `merge`: merges
- **History:**
  - Make one commit per feature, with no intermediate WIP commits; use `--amend` or squash.
  - Pull with `--rebase`.
  - Squash before merging into the main branch.
  - Never force-push to shared branches.
